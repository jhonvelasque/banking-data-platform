# 7. Integración y Despliegue Continuo (CI/CD) para el Pipeline Bancario (CI/CD for the Banking Pipeline)

Esta sección cubre el diseño y la automatización del ciclo de vida del proyecto mediante la integración y el despliegue continuo (CI/CD) utilizando **Google Cloud Build** y **GitHub**.

---

## Estructura de Componentes en el Proyecto

*   **Configuración de Pipeline de Despliegue (GCP Cloud Build):** [cloudbuild.yaml](../cloudbuild.yaml)

---

## 1. Concepto y Rol de Cloud Build y GitHub

Para asegurar la confiabilidad del código y evitar despliegues manuales propensos a errores humanos, implementamos un flujo de integración continua:
*   **Repositorio GitHub:** Controla el versionamiento de los archivos DAG, scripts de Spark y transformaciones SQL de BigQuery.
*   **GCP Cloud Build:** Es el servicio sin servidor (*serverless*) que actúa como motor de CI/CD. Al registrar un nuevo cambio (*commit*) o fusión (*merge*) en el repositorio, se dispara un disparador (*trigger*) de Cloud Build que realiza la compilación y despliegue del software en los recursos activos de GCP.

---

## 2. Flujo de Trabajo Detallado de `cloudbuild.yaml`

El archivo `cloudbuild.yaml` define cuatro tareas automatizadas en orden secuencial:

### Tarea 1: Creación / Verificación del Entorno de Cloud Composer (`create-composer-env`)
*   **Comando:** `gcloud composer environments describe` y `gcloud composer environments create`.
*   **Acción:** Comprueba si el entorno administrado de Apache Airflow (Cloud Composer) ya existe en GCP. Si no está creado, inicia su aprovisionamiento automáticamente con el tamaño de nodo y la imagen de versión especificados.

### Tarea 2: Consulta del Bucket de Composer (`fetch-composer-bucket`)
*   **Comando:** `gcloud composer environments describe --format="value(config.dagGcsPrefix)"`.
*   **Acción:** Consulta a la API de GCP para obtener la ruta del bucket de Google Cloud Storage asignado al entorno de Cloud Composer (cada entorno Composer crea automáticamente un bucket para almacenar los códigos). Limpia el prefijo `gs://` y la subcarpeta `/dags` y guarda el nombre del bucket limpio en un archivo temporal.

### Tarea 3: Despliegue de los DAGs de Airflow (`deploy-dags`)
*   **Comando:** `gsutil -m rsync -r -d airflow/dags/ gs://<COMPOSER_BUCKET>/dags/`.
*   **Acción:** Sincroniza la carpeta local de Airflow DAGs del repositorio con la subcarpeta `/dags` del bucket del servidor Cloud Composer. El parámetro `-d` (delete) asegura la eliminación de DAGs en GCP si fueron borrados localmente en GitHub, manteniendo sincronizada la versión exacta.

### Tarea 4: Despliegue de Scripts SQL y Spark (`deploy-data`)
*   **Comando:** `gsutil -m rsync -r -d airflow/data/ gs://<COMPOSER_BUCKET>/data/`.
*   **Acción:** Sincroniza todas las carpetas con scripts adicionales de procesamiento de datos (los pipelines de Dataflow en `/dataflow`, los jobs de Spark en `/dataproc`, y las consultas de BigQuery en `/bigquery`) hacia la carpeta `/data` del bucket de Composer, poniéndolas a disposición del orquestador.

---

## 3. Prácticas de Producción para CI/CD

*   **Validación Local de Sintaxis:** Antes de subir cualquier cambio al repositorio, se ejecuta una validación rápida de la sintaxis de Python para evitar fallos de compilación en Airflow:
    ```bash
    python -m compileall airflow pubsub
    ```
*   **Seguridad de Credenciales:** El archivo `cloudbuild.yaml` y los scripts de Airflow no contienen credenciales fijas. Todas las contraseñas operacionales de la base de datos se consumen dinámicamente mediante **Secret Manager**, al cual el entorno de Composer accede de forma segura mediante políticas de permisos IAM configuradas.
